# Marcle-Plan-Review

以用户当次 review instruction 确定范围和关注点；本 skill 只辅助查漏和收敛，不替代 instruction、不另写一套计划。默认中文、短平快；只读，不修改文档或实施代码，除非用户另行授权。

## 审查视角

按相关性使用以下五条，不机械逐条打分或输出：

- **统一能力入口**：多个调用者复用所属模块的公开能力，不各自实现一套，也不集中成全局“大总管”。
- **收敛状态修改路径**：同一事实的修改有明确通道，校验、提交和结果收敛不散落竞争。
- **明确模块所有权**：状态、生命周期与失败处理有负责人；读取或订阅不等于拥有修改权。
- **清除旁路写入**：不绕过公开接口修改内部状态；被替代的路径有明确退休边界，不默认保留兼容层。
- **按需控制复杂度**：按真实用户规模与核心需求设计，不为低概率边缘场景或微小体验收益引入高成本机制；必要的数据、费用和操作正确性不能省略。

同时关注：本期必要与可后置是否分清；关键前置能力是否真实存在；检查点能否闭合并尽早经过真实生产流程验收。不要把普通实现细节都要求 planner 预先指定。

## 证据与收敛

针对影响结论的假设，定向核对相关代码或契约；不默认启动全仓审计或全量测试。区分已确认缺口与待核实事项，不把缺少证据写成确定缺陷。

阻塞项须说明具体失败机制、用户后果、为何本期必须处理，并给出最窄调整方向。原则不是要求新增接口或重构的理由；不要主动添加框架、兼容、自动恢复或体验包装。高成本方案先考虑限制行为、明确失败、手动重试是否足够。

## 输出

先给 **Approved** 或 **Changes Requested**，说明当前范围是否可执行；未审查范围不作保证。

有必要问题时，简列 P0/P1/P2、文档位置及必要的代码证据、产品影响和最窄建议。只有阻塞执行或验收的缺口才阻止通过，非阻塞建议明确标注，不自动成为实施要求。没有必要问题就简短通过，不凑发现；除非用户要求，不输出长教程或 coder instruction。
